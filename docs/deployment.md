# Deployment — Render (API + PostgreSQL) and Vercel (dashboard)

| Piece | Host | Notes |
|---|---|---|
| PostgreSQL | Render (from `render.yaml`) — or Neon/Supabase | Must be UTF-8 (the default on managed hosts) |
| API (this repository) | Render web service, Node 24 | Runs the evaluation worker in the same process |
| Dashboard ([atlasguard-frontend](https://github.com/kobiowuquadri/atlasguard-frontend)) | Vercel | Proxies `/api/*` to the API, so the session cookie is first-party |
| N-ATLaS inference | GPU host — the Kaggle notebook for demos | See [natlas-integration.md](natlas-integration.md). Never deploy the 8B model on the API host |

## What you need before starting

* Both repositories **pushed to GitHub**. Render and Vercel deploy from GitHub; private
  repositories work — grant access when you connect your GitHub account.
* A Render account and a Vercel account (free plans are enough to start — read the limits below).
* The email address you will sign up with (it becomes the administrator).
* For evaluations: a running N-ATLaS endpoint (`NATLAS_BASE_URL` + `NATLAS_API_KEY` from the
  Kaggle notebook). The API starts without it; runs simply cannot start until it is set.

Order: **1** API + database on Render → **2** dashboard on Vercel → **3** tell the API the
dashboard URL → **4** connect N-ATLaS → **5** verify.

## 1. API and database on Render

1. Render dashboard → **New → Blueprint** → connect GitHub → choose **atlasguard-backend**.
   Render reads [`render.yaml`](../render.yaml) and proposes `atlasguard-db` (PostgreSQL) and
   `atlasguard-api` (web service), both in Frankfurt (closest to Nigeria).
2. Fill in the values Render asks for:

   | Variable | Value now |
   |---|---|
   | `APP_ORIGINS` | leave empty for now — set in step 3 |
   | `ADMIN_EMAILS` | your email, e.g. `you@example.com` |
   | `NATLAS_BASE_URL`, `NATLAS_API_KEY` | from the Kaggle notebook, or empty for now |
   | `NATLAS_MODEL_REVISION` | empty (the inference service reports it) |

   `API_KEY_PEPPER` is generated by Render; `DATABASE_URL` is wired to the database.
3. **Apply**. The first build takes several minutes. On start the API runs
   `prisma migrate deploy`, imports the official Nigerian Context Benchmark and creates the
   N-ATLaS model configuration.
4. Note the service URL (e.g. `https://atlasguard-api.onrender.com`; Render adds a suffix if the
   name is taken) and open `<url>/api/v1/health` — it should return `"status": "ok"`.

## 2. Dashboard on Vercel

1. Vercel → **Add New → Project** → import **atlasguard-frontend** (framework: Next.js, detected).
2. **Environment variables** — add them *before* the first deploy:

   | Variable | Value |
   |---|---|
   | `ATLASGUARD_API_URL` | the Render URL from step 1.4 — no trailing slash, no `/api/v1` |
   | `SESSION_COOKIE_NAME` | `ag_session` |

   `ATLASGUARD_API_URL` is read when the dashboard is **built** (it defines the `/api` proxy), so
   after changing it you must **redeploy**.
3. **Deploy**, then note the production URL (e.g. `https://atlasguard.vercel.app`).

## 3. Tell the API where the dashboard is

Render → `atlasguard-api` → **Environment** → `APP_ORIGINS` = the Vercel production URL
(comma-separate several; no trailing slash) → **Save** (the service restarts). Without this,
signing in works but every change (creating a project, starting a run) fails with
`403 Cross-site request blocked`.

## 4. Connect N-ATLaS

Start the Kaggle notebook ([natlas-integration.md](natlas-integration.md) §3). When its last
cell prints `NATLAS_BASE_URL` and `NATLAS_API_KEY`, put both on Render (**Environment → Save**).
Every new Kaggle session prints a **new** URL and key — update them each time.

## 5. Verify

- [ ] `https://<dashboard>/api/v1/health` → `ok`; `/api/v1/ready` → `ready`
- [ ] `https://<dashboard>/api/v1/model/status` → N-ATLaS `available`, served model `NCAIR1/N-ATLaS`
- [ ] sign up with the `ADMIN_EMAILS` address; *Settings* shows **Administrator**
- [ ] no "Development mode" banner (fixtures are always off in production)
- [ ] create a project, run a small evaluation with the N-ATLaS configuration, export
      *N-ATLaS integration evidence* from the run page into `evidence/integration/`
- [ ] share the dashboard URL and [testing-guide.md](testing-guide.md) with testers

## Free-plan limits and what they mean

| Limit | Effect | What to do |
|---|---|---|
| Render free web services **sleep after 15 minutes without requests** (≈1 min to wake) | The first visit after a quiet period is slow or times out once; the in-process worker pauses while asleep, so an unattended run stalls | Keep the dashboard open while a run executes (it polls the API), ping `/api/v1/health` every 10 minutes with a free uptime monitor, or use the **Starter** plan for the judging period |
| Render free **PostgreSQL expires after 30 days** | The database (users, runs, evidence) is deleted | Upgrade the database before it expires, or use Neon/Supabase (set `DATABASE_URL` yourself and remove the `databases` block) |
| **Simulated fixtures are disabled in production** | Without a reachable N-ATLaS endpoint nobody can start a run (status shows *unavailable*) | Run the Kaggle notebook during tester sessions, demos and judging |
| Kaggle sessions end (idle/≈12 h); quick-tunnel URLs change | Model status turns *unavailable* | Re-run the notebook and update the two variables on Render |
| Vercel preview deployments get their own URLs | Previews are not in `APP_ORIGINS` (403 on changes) | Test on the production URL, or add the preview URL to `APP_ORIGINS` |

## Troubleshooting

| Symptom | Cause / fix |
|---|---|
| Render build: `nest: not found` or `tsc: not found` | `NODE_ENV=production` makes pnpm skip devDependencies; the build command must install with `NODE_ENV=development` (as in `render.yaml`) |
| API exits with `Invalid AtlasGuard API configuration` | The message lists each variable; in production `API_KEY_PEPPER` must be ≥ 32 characters |
| Dashboard pages show "Couldn't load this data" / `/api/…` 404 | `ATLASGUARD_API_URL` missing or wrong at build time — fix it on Vercel and redeploy |
| Signed in, but actions fail with `403 Cross-site request blocked` | Add the dashboard URL to `APP_ORIGINS` on Render |
| Runs fail to start with `MODEL_PROVIDER_UNAVAILABLE` / `NOT_CONFIGURED` | The Kaggle session stopped or the two variables are out of date |
| First request after a while takes ~1 minute | The free Render instance was asleep (see above) |

## Other hosts

The API also ships a Dockerfile (`docker build -f apps/api/Dockerfile -t atlasguard-api .`); it
runs `prisma migrate deploy` before starting. Production environment variables:

| Variable | Value |
|---|---|
| `NODE_ENV` | `production` |
| `DATABASE_URL` | managed PostgreSQL URL (`?sslmode=require` on most hosts) |
| `APP_ORIGINS` | the dashboard origin(s) |
| `TRUST_PROXY` | `true` behind a load balancer |
| `API_KEY_PEPPER` | 32+ random characters (`node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"`) |
| `ADMIN_EMAILS` | administrator email(s) |
| `NATLAS_BASE_URL`, `NATLAS_API_KEY` | the inference endpoint |
| `NATLAS_MAX_CONCURRENCY` | `1` for the AtlasGuard inference service |

Cookies are `Secure` automatically in production, and fixtures cannot be enabled there.
